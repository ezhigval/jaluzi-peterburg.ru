# Руководство администратора

## Авторизация

### Вход в админ-панель

1. Откройте страницу `/admin/login`
2. Введите email и пароль
3. После успешного входа вы будете перенаправлены на запрошенную страницу

### Защита админ-режима

Все URL вида `/:slug/admin` (например, `/gorizontal/admin`) защищены и требуют авторизации.

При попытке доступа без авторизации произойдет автоматический редирект на `/admin/login?next=/:slug/admin`.

После входа вы будете перенаправлены обратно на запрошенную страницу.

## Создание первого администратора

### Через SQL

Подключитесь к базе данных PostgreSQL:

```bash
psql -U jaluzi -d jaluzi_db
```

Создайте пользователя с хешем пароля (пример для пароля `admin123`):

```sql
-- Хеш для пароля "admin123" (bcrypt, cost 10)
INSERT INTO users (email, password_hash, role)
VALUES (
  'admin@example.com',
  '$2a$10$N9qo8uLOickgx2ZMRZoMyeIjZAgcfl7p92ldGxad68LJZdL17lhWy',
  'admin'
);
```

### Генерация хеша пароля (Go)

Если нужно создать хеш для другого пароля:

```go
package main

import (
    "fmt"
    "golang.org/x/crypto/bcrypt"
)

func main() {
    password := "your_password_here"
    hash, _ := bcrypt.GenerateFromPassword([]byte(password), bcrypt.DefaultCost)
    fmt.Println(string(hash))
}
```

Или используйте онлайн-генератор bcrypt.

## Как работает авторизация

### Хранение токена

JWT токен хранится в **httpOnly cookie** с именем `auth_token`:
- Безопасность: JavaScript не может получить доступ к cookie
- Автоматическая отправка: браузер автоматически отправляет cookie с каждым запросом
- Срок действия: 24 часа

### Проверка авторизации

1. Frontend: компонент `AuthGuard` проверяет авторизацию через `/api/v1/auth/me`
2. Backend: middleware `AuthMiddleware` проверяет токен из cookie или Authorization header
3. При невалидном токене возвращается 401 Unauthorized

### Rate Limiting

Эндпоинт `/api/v1/auth/login` защищен rate limiting:
- **5 попыток** за **15 минут** с одного IP
- При превышении лимита возвращается 429 Too Many Requests

## Логирование

Все попытки входа логируются:
- Успешные входы: `INFO` уровень с email и user_id
- Неудачные попытки: `WARN` уровень с email и ошибкой

Логи доступны в stdout/stderr сервера (в production рекомендуется настроить централизованное логирование).

## Безопасность

### Рекомендации для production

1. **HTTPS обязателен**: Cookie с `Secure` флагом работает только по HTTPS
2. **Сильные пароли**: Используйте сложные пароли для администраторов
3. **Регулярная ротация**: Периодически меняйте пароли
4. **Мониторинг**: Следите за логами на подозрительную активность
5. **Ограничение IP**: Рассмотрите возможность ограничения доступа к админке по IP (на уровне Nginx)

### Настройка для development

В development режиме (HTTP) cookie работает без `Secure` флага, что позволяет тестировать локально.

## Выход из системы

Для выхода из системы используйте эндпоинт:

```bash
POST /api/v1/auth/logout
```

Или просто удалите cookie `auth_token` в браузере.

## Структура ролей

Текущие роли:
- `admin` - полный доступ ко всем функциям
- `manager` - ограниченный доступ (запланировано)

В будущем можно расширить систему ролей и прав доступа.

## Troubleshooting

### Не могу войти в админку

1. Проверьте, что пользователь создан в БД
2. Проверьте правильность email и пароля
3. Проверьте логи backend на наличие ошибок
4. Убедитесь, что rate limit не превышен (подождите 15 минут)

### Токен не сохраняется

1. Проверьте настройки CORS на backend
2. Убедитесь, что `credentials: 'include'` используется в fetch запросах
3. В production проверьте, что используется HTTPS

### Редирект на логин не работает

1. Проверьте, что компонент `AuthGuard` используется на страницах админки
2. Проверьте, что эндпоинт `/api/v1/auth/me` работает
3. Проверьте консоль браузера на наличие ошибок
